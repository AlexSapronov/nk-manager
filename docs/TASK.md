# Техническое задание: менеджер Национального каталога «Честного знака»

**Версия постановки:** 1.0 · 24 октября 2026 года  
**Назначение:** полный промпт/ТЗ для агента-разработчика.  
**Проект:** новое внутреннее веб-приложение (рабочее название `nk-manager`).  
**Организация:** одна организация, работающая с российским Национальным каталогом маркированных товаров (НК ГИС МТ); не путать с Национальным каталогом товаров Казахстана.  
**Приоритет:** ежедневное удобство сотрудников, надёжность данных и реальная интеграция, а не максимальное число кнопок.

> **Задание агенту.** Спроектируй, реализуй, протестируй и документируй новое веб-приложение для массового создания карточек в Национальном каталоге, доработки существующих черновиков и полного прохождения их жизненного цикла до публикации. Обязателен отдельный этап согласования UI/UX-прототипа **до** реализации основного функционала. Не выдавай макет, тестовый мок или предполагаемую поддержку API за проверенную промышленную интеграцию.

| 6 | Точные и похожие PN дают предупреждение, но сотрудник может подтвердить, что товар другой, и продолжить; все решения записываются |

**Урок предыдущего проекта:** спецификация UI и нестандартных сценариев обязательна, проверка реального интерфейса происходит **до** реализации интеграций; нельзя приравнивать «кнопка есть» к «процесс завершён».

## 1. Цель и границы

### 1.1. Результат для бизнеса

Приложение должно выполнять три основных процесса:

1. **Формирование шаблонов по ТН ВЭД на основе реального каталога.** Выгрузить максимально полные карточки компании из НК, передать экспорт внешнему агенту на анализ, импортировать предложенные им шаблоны, проверить и утвердить их. Внутри приложения не требуется LLM/ИИ. Шаблон должен быть управляемым, версионируемым, проверяемым.
2. **Создание новых карточек.** Одну вручную либо множество из Excel; применить шаблон по ТН ВЭД, дополнить индивидуальные поля, проверить возможные дубли, использовать предоставленный GTIN либо легально получить новый, отправить в НК, пройти модерацию, подписать и опубликовать.
3. **Дозаполнение существующих черновиков.** Получить их из НК, подобрать шаблоны, заполнить только отсутствующие значения, показать изменения, массово отправить подходящие карточки на модерацию, обработать замечания и опубликовать. **Никогда не создавать новый товар взамен исходного черновика по ошибке.**

Пользователи — сотрудники, работающие с товарными карточками, и администратор. Сотрудники имеют право самостоятельно проводить **все** этапы, включая массовую публикацию. Администратор управляет конфигурацией, шаблонами, доступами и проблемными операциями, но не является обязательным согласующим лицом публикации.

### 1.2. Что входит в первую полноценную версию

- Подключение к российскому НК, полный импорт/синхронизация карточек, включая черновики, статусы и варианты версий там, где их предоставляет API.
- Одна общая корпоративная база карточек с поиском, фильтрами, назначением ответственных и журналом действий.
- Экспорт корпуса существующих карточек для внешнего агента, импорт и утверждение шаблонов по десятизначному ТН ВЭД (с учётом категории и типа карточки).
- Создание карточки вручную и Excel-импорт с предпросмотром, сохранёнными схемами сопоставления колонок, валидацией и контролем дублей.
- Массовое дозаполнение существующих черновиков по шаблонам с предварительным просмотром различий.
- Проверка точных/похожих PN перед созданием карточки, созданием нового GTIN и доработкой черновиков.
- Процессы модерации, исправления замечаний, подписания, публикации и проверки фактического статуса, насколько подтверждены официальными методами НК.
- UI/UX с компактным реестром и боковой панелью, режимом полноэкранного редактирования, массовыми операциями, прозрачными ошибками.
- Админка, аудит, долговечная очередь, резервное копирование, сценарии отказов и проверяемое обновление приложения.

### 1.3. Чего не делать без отдельного подтверждения

- Не встраивать платный/облачный ИИ или автоматическую отправку карточек на внешний ИИ-сервис: **анализ проводит внешний агент после явного экспорта**.
- Не придумывать значения технических характеристик, изображения, документы соответствия или принадлежность товара к категории.
- Не генерировать GTIN локальным алгоритмом, не подставлять «похожие» чужие GTIN.
- Не переносить в новое приложение бизнес-логику эмиссии КМ, АТК, таможни и складского сканирования. Нужна лишь повторно используемая инфраструктура доступа к ЧЗ, подписи, очередей, аудита и интерфейсных компонентов, если она подходит.
- Не создавать публичный деморежим с вымышленными «успешными ответами НК». Подмены API допустимы **только внутри тестов** и явно обозначенных статических UI-прототипов.
- Не модифицировать существующий `marking-bm` или его рабочую базу без отдельного обоснования и разрешения. Это новый проект с независимой схемой хранения и развёртыванием.

## 2. Обязательный старт: исследование настоящего API НК

**Это блокирующий этап № 0.** Перед объявлением какой-либо операции «реализованной» найди и прочитай актуальную документацию **российского**, а не казахстанского Национального каталога. Укажи точную версию/дату, URL документа, права, параметры, примеры ответов и ограничения. Документация может быть доступна в личном кабинете компании; если она недоступна в среде агента, составь список необходимых документов и реализуй сначала независимые локальные функции, не изобретая endpoint'ы.

Проверь и оформи отдельную **матрицу подтверждённых возможностей**:

| Операция | Что должен выяснить агент | Результат исследования |
|---|---|---|
| Авторизация НК | Отдельный механизм НК, токены/сертификаты, полномочия, время жизни доступа | Документированный контракт |
| Получение каталога | Постраничное перечисление опубликованных товаров и всех доступных версий, фильтры | Контракт + реальный read-only ответ |
| Получение черновиков | Фильтры по статусам, ID карточки и ID версии | Контракт + реальный read-only ответ |
| Атрибутная схема | Методы получения типов полей, обязательности, значений справочников и зависимостей от ТН ВЭД/категории | Контракт/ограничения |
| Создание карточки | Типы товара, обязательные начальные поля, схема получения внешнего ID | Контракт + тест в разрешённой среде |
| Изменение черновика | Допустимые поля и операции обновления именно существующей версии | Контракт |
| Массовые операции | API/пакетные возможности, лимиты, разбор частичного успеха | Контракт |
| Новые GTIN | Право компании, выбранная мастер-система GS1/НК, операция выделения кода, необратимость | Подтверждённая процедура |
| Модерация | Отправка, статусы, замечания по полям | Контракт |
| Подпись/публикация | Какие точные данные и каким сертификатом подписываются, как подтверждается публикация | Контракт + реальный тест |
| Редактирование опубликованной | Версионирование, неизменяемые поля, ограничения | Контракт |

Важно: **поддержка действия в интерфейсе ЛК не доказывает наличия равнозначного API**. Полный цикл через приложение остаётся целевой функцией. Если какой-то этап в API реально отсутствует, не симулируй успех: документируй blocker, предоставь безопасную подготовку/экспорт и прямую ссылку на соответствующую страницу ЛК, но не объявляй весь цикл полностью автоматизированным или принятым.

Приоритет источников: официальная документация НК в ЛК и на `https://апи.национальный-каталог.рф/`, официальные инструкции НК на `docs.crpt.ru` и публикации `markirovka.ru`. Не использовать казахстанские `nationalcatalog.kz` или `developer.nct.kz` для российского проекта.

## 3. Базовая модель пользователей и прав

**Принять за стартовую совместимую модель с `marking-bm`:** сотрудники входят по заранее созданному username без пароля во внутреннем корпоративном контуре; администрирование защищено **дополнительным отдельным паролем** и полноценной серверной сессией. Отсутствие пароля у сотрудника — осознанный компромисс, не доказательство физической личности; если возможно, предусмотреть без изменения бизнес-логики подключение корпоративного SSO в будущем.

В отличие от персональных накладных, каталог товаров организации общий: чтобы предотвращать дубли, каждый сотрудник должен иметь возможность **искать и просматривать** опубликованные карточки и черновики организации. Для изменения незавершённых карточек предусмотреть ответственного и механизм «взять в работу»/«освободить»; администратор может назначить другого ответственного. Не скрывать существование карточек другого сотрудника от поиска дублей. Несколько сотрудников не должны молча перезаписывать одну версию.

### 3.1. Матрица ролей

| Действие | Сотрудник | Администратор |
|---|---|---|
| Просмотр/поиск всех карточек компании, статусов, GTIN, PN | Да | Да |
| Создание одной карточки и импорт партии Excel | Да | Да |

| Редактирование чужого черновика | После взятия в работу с контролем конкурентного доступа | Да, с аудитом |
| Массовое применение утверждённых шаблонов | Да | Да |
| Проверка и подтверждение возможного дубля | Да; требуется причина/подтверждение | Да |
| Запрос нового GTIN, если поддержан и разрешён | Да после проверки дублей и явного подтверждения | Да |
| Отправка на модерацию | Да, в том числе массово | Да |
| Исправление замечаний модерации | Да | Да |
| Подписание и публикация | Да, через централизованный подписант, в том числе массово | Да |
| Экспорт опубликованного/чернового каталога для анализа | Да, если это допустимо корпоративными правами; факт экспорта журналируется | Да |

На сервере проверять роль **для каждого метода и каждой загрузки файла**; скрытие кнопок в интерфейсе не заменяет авторизацию. Сессии пользователя аннулируются при его отключении/смене роли. Отдельно защищать API локального Windows-подписанта; ни сотрудник, ни пользователь с обычной сессией не может передать ему произвольный payload.

## 4. Основные сущности и данные

Построить не «одну универсальную JSON-таблицу», а понятную предметную модель с возможностью хранить структурированные атрибуты:

1. `catalog_items`: внутренняя запись товара, PN, канонизированные ключи поиска, GTIN (если есть), 10-значный ТН ВЭД, товарная группа/категория, тип карточки, ответственный, источник, идентификаторы НК.
2. `card_versions`: ID карточки НК, ID версии/черновика (если существуют отдельно), актуальный статус НК, ревизия, время синхронизации, редактируемые и заблокированные поля; одна карточка может иметь опубликованную и редактируемую версии одновременно.
3. `attributes`: код/тип атрибута НК, значение, единица измерения/справочник, происхождение значения (`nk`, `excel`, `employee`, `template`, `agent_import`), статус проверки, timestamp.
4. `attribute_schemas`: версии реально полученных схем по категории/типу и ТН ВЭД, обязательность, зависимые поля, справочники/ограничения.
5. `templates` и `template_versions`: привязка к полному десятизначному ТН ВЭД, категории, типу карточки, версия/статус, список правил заполнения, источники/обоснование.
6. `import_batches`/`import_rows`: исходный Excel, выбранный лист, схема колонок, исходные значения, нормализованные значения, ошибки, подтверждения дублей, локальные ID создаваемых карточек.
7. `catalog_exports`: сохранённая выгрузка, дата, выбранный объём, формат/версия схемы, контрольная сумма.
8. `duplicate_candidates` и `duplicate_decisions`: идентификаторы сравниваемых карточек, причины сходства, ответ пользователя и его комментарий.
9. `operations`/`receipts`: исходный payload/hash, тип действия, контекст пользователя, состояние отправки, внешний ID/квитанция, отложенные/ошибочные/неизвестные результаты.
10. `assignments`/`audit`: ответственность, версии изменений и кто инициировал операции; синхронизация каталога не должна затирать локальную историю.
11. `attachments`: изображения/разрешительные документы, исходные файлы, ссылки и метаданные по правилам API, контрольные суммы, права доступа.

GTIN и ТН ВЭД хранить **строками**, не числами Excel: сохранять ведущие нули. PN хранить точное исходное написание плюс отдельный нормализованный поисковый ключ. Не изменять формат PN в оригинальных данных без явного действия.

## 5. Синхронизация существующего каталога

### 5.1. Первый запуск

В админке: настроить компанию и доступы НК → «Проверить подключение» → «Получить каталог» → прогресс импорта/сводка. Загрузить все доступные компании опубликованные карточки, черновики, карточки «Требует изменений», «Ожидает подписания» и другие статусы, описанные API. Не пропускать записи из-за постраничных лимитов; хранить cursor/page, последние успешные этапы, время и версию схемы.

Синхронизация **read-only** сама по себе не меняет данные в НК. Каждая запись получает стабильную привязку к внешним ID. Последующие синхронизации обновляют статус и изменения, не плодят дубликаты локальных записей.

### 5.2. Ежедневное использование

- Автоматическая периодическая синхронизация с разумными лимитами API; ручная кнопка «Обновить» доступна в реестре.
- На экране видны «Последняя синхронизация», прогресс, ошибки и то, насколько сведения свежие.
- Если сотрудник редактирует карточку, а в НК появилась новая ревизия, показывать сравнение и конфликт; не заменять локальные изменения молча.
- Если локальная операция неизвестна из-за потери ответа, сначала искать следы действия по внешнему ID/карточке/версии и журналу, не посылать команду заново.
- Если через API нельзя получить **полную** историю или все поля, это честно обозначается; разрешить **загрузку официальной полной XLSX-выгрузки из ЛК** как дополнение к API. Приложение должно уметь её разбирать, не выдавая её за прямой API-ответ.

### 5.3. Целостность

Сохранять: первоначальный внешний ID, версию, текущее состояние, исходные ошибки НК, дату последнего подтверждения. При двух версиях карточки показывать **одну логическую запись с явным переключением «Опубликованная / Черновая»**, а не два непонятных дубля.

## 6. Экспорт для внешнего агента и управление шаблонами

### 6.1. Экспорт существующего корпуса

Раздел «Шаблоны» → «Экспортировать каталог для анализа»:

- Выбор всех опубликованных карточек или фильтра по ТН ВЭД, категориям, типу, статусу и наличию значений; по умолчанию предпочтительно опубликованные как более качественный источник.
- Экспорт структурированного **JSON** с полнотой полей, справочными ID, типом, версией схемы и статусом; дополнительно человекочитаемый XLSX/CSV со сводкой. Если некоторые поля невозможно выгрузить, включить `unavailable_fields`/причину.
- Экспортировать для каждой карточки уникальный внешний ID, PN (если присутствует), GTIN, ТН ВЭД, тип, категорию, набор атрибутов, источник/статус, даты, но не ключи API, токены или внутренние секреты.
- Сохранить манифест: версия формата, число карточек, распределение по ТН ВЭД, время, hash; дать пользователю один ZIP с JSON, XLSX, схемой и README для внешнего агента.
- Предложить администратору проверить состав выгрузки на коммерчески чувствительные сведения перед передачей внешнему агенту. Никакой автоматической передачи внешнему LLM.

### 6.2. Формат импортируемого шаблона

Создать документированную переносимую схему JSON (опубликовать JSON Schema), например логически:

```json
{
  "schema_version": 1,
  "name": "Шаблон соединителей",
  "tnved10": "8536901000",
  "category_id": "ACTUAL_CATEGORY_ID_FROM_NK",
  "card_type": "unit",
  "rules": [
    {
      "nk_attribute_id": "ACTUAL_ATTRIBUTE_ID_FROM_NK",
      "mode": "fill_if_empty",
      "value": "REFERENCE_VALUE_FROM_REAL_CATALOG",
      "source_count": 187,
      "comment": "Подтвердить по каталогу и справочнику НК"
    }
  ]
}
```

**Это схема-пояснение, не пример действительных ID НК.** Агент-разработчик обязан заменить символические названия реальными из документации/схемы, предусмотреть типизацию (число/текст/справочник/перечень/изображение/сложный объект) и опциональную уверенность/обоснование.

Допускаются режимы правила: `fill_if_empty`, `suggest_only`, `required_input`, `derived_from_explicit_field` (только верифицированная формула), `never_autofill`. Предложения внешнего агента **не** обладают приоритетом над требованиями НК.

### 6.3. Проверка и утверждение шаблонов

- Предпросмотр импортированного шаблона без его применения; выявление несуществующих атрибутов, невалидных справочных значений, несовпадения типа/категории/ТН ВЭД, неизвестных зависимостей и ошибок структуры.
- Экран «Было / Предлагается / Применимо» с проверкой на 3–5 реальных тестовых карточках из экспортного набора, без записи в НК.
- Администратор утверждает версию, отклоняет или возвращает на доработку. Утверждённая версия неизменяема; новая версия создаётся отдельно с diff; предусмотрен быстрый откат активной версии.
- Для одного ТН ВЭД допускаются варианты шаблона по категории/типу карточки; отсутствие валидного шаблона не должно приводить к применению чужого шаблона.
- Не копировать из старых карточек уникальные поля, GTIN, PN, модель, конкретные мощности/напряжения, изображения или разрешительные документы автоматически, если данные не являются заведомо общими и подтверждёнными для данной карточки.
- Система не обязана сама анализировать частоты и выводить паттерны; это задача внешнего агента. Внутри достаточно верификации предложенных правил, управляемых версий и просмотра статистики экспорта.

## 7. Создание одной новой карточки

1. Сотрудник нажимает **«Создать карточку»**.
2. Выбирает тип карточки, ТН ВЭД (10 цифр), категорию товара, вводит PN и известные начальные реквизиты. Учитывать доступные типы и ограничения группы по официальной схеме НК; не считать, что любой тип разрешён всегда.
3. **До генерации GTIN или записи в НК** выполнить точный/нечёткий поиск по корпоративному каталогу, включая черновики, опубликованные версии и локальные ещё не отправленные карточки.
4. Сотрудник просматривает совпадения и может открыть существующую карточку, выбрать её для доработки либо подтвердить «Это другой товар»; причина/решение логируются. Предупреждение **не является безусловной блокировкой даже при точном совпадении PN**, согласно согласованному правилу.
5. Применяется подходящий утверждённый шаблон, только к пустым подходящим полям. Индивидуальные поля заполняет сотрудник.
6. Проверка обязательных полей, типов, допустимых справочников, ограничений и связей. Показать компактный список «Что ещё заполнить» с переходом к полям.
7. Если GTIN введён — проверить формат и существующие привязки; если отсутствует — предложить официальный процесс получения нового **только при подтверждённой доступности и правах компании**. Нельзя придумывать GTIN самому.
8. Перед реальной отправкой показать итоговый обзор (особенно неизменяемые после создания поля), явное подтверждение; затем отправить, сохранить внешний ID и проверить результат.
9. Продолжить жизненный цикл карточки: черновик → модерация → исправления → подпись → опубликована. Доступность действий зависит от подтверждённого статуса НК.

**Спорная исходная информация:** если выбор типа, бренда, части ТН ВЭД и т. п. становится необратимым в НК, предупредить **до отправки** и блокировать попытки редактирования после создания. Не имитировать успешную локальную правку серверного неизменяемого поля.

## 8. Массовый импорт новых товаров из Excel

### 8.1. Мастер импорта — четыре коротких шага

**Шаг 1. Файл:** загрузка XLSX, выбор листа, определение строки заголовков, предварительный просмотр 10–20 строк; корректное чтение строковых/числовых ячеек без потери ведущих нулей GTIN.

**Шаг 2. Сопоставление:** автоматически предложить PN, GTIN (опционально), ТН ВЭД, тип/категорию, наименование, бренд и остальные поля. Сотрудник может переопределить соответствие; сохранять схему импорта пользователя. Не требовать жёсткого порядка колонок. Сохранять необработанные исходные строки/имена колонок для аудита.

**Шаг 3. Проверка:** поиск дублей внутри файла и по существующему каталогу, выбор шаблона для каждой категории/ТН ВЭД, проверка справочников и обязательных характеристик, итоговая таблица конфликтов. Разделить проблемы на блокирующие ошибки (невалидный обязательный атрибут), предупреждения (сходство PN) и корректные строки.

**Шаг 4. Подтверждение:** вывести, сколько будет создано новых карточек, сколько строк останется в работе, сколько GTIN потребуется запросить. Отдельное явное подтверждение создания и **отдельное подтверждение выдачи новых GTIN**, если применимо. Запуск фоновой долговечной партии, детальный результат по каждой строке.

### 8.2. Действия после импорта

- Общий реестр карточек, фильтр «Импорт №…», массовое заполнение недостающих данных, переход к отдельной строке в боковой панели.
- Не повторять успешное создание карточки после таймаута другой строки; связывать внутреннюю запись с внешним ID и локальным idempotency-key.
- Позволить выгрузить «Ошибки импорта.xlsx»: номер исходной строки, PN, проблема, предлагаемые действия.
- Загруженный Excel можно повторно открыть как источник, но повторный импорт того же файла не должен молча создавать дубли.
- Для невалидных/неподдерживаемых типов ячеек: показывать исходное и предлагаемое преобразованное значение, не делать необратимое автоматическое округление или преобразование идентификатора.
- Не создавать карточки из строк, для которых ещё не получено явное разрешение пользователя по предупреждениям о дублях.

## 9. Массовое дозаполнение существующих черновиков

1. Фильтр **«Черновики НК»**; синхронизировать актуальные версии и статусы; выбрать конкретные карточки, в том числе сотни.
2. Приложение подбирает утверждённые шаблоны по ТН ВЭД/категории/типу; не использует неподходящие шаблоны молча.
3. Формирует **план изменений**: сколько значений будет вставлено, какие уже существовали, где конфликт/невалидное поле/неподдерживаемая схема.
4. По умолчанию заполнение **только пустых полей**, без перезаписи пользовательских/удалённых/полученных из НК значений. Существующие, но ошибочные поля отдельно пометить «требуют исправления»; для них нужен явный ручной выбор значения.
5. Перед записью дать групповой предпросмотр: карточки «Готовы», «Нужна информация», «Конфликт», «Возможный дубль опубликованной карточки». Предупреждения можно подтвердить индивидуально либо массово после просмотра.
6. По подтверждению сохранить изменения **в исходных версиях черновиков НК**. Не создавать другие GTIN/карточки и не терять исходный внешний ID.
7. Готовые после проверки карточки можно выделить и **массово отправить на модерацию**. Ошибки одной карточки не блокируют независимые остальные; результаты каждой показывать отдельно.
8. Если карточка отклонена модерацией, сохранить замечания, подсветить соответствующие поля, разрешить исправить и отправить повторно.
9. Если синхронизация обнаружила опубликованную карточку с тем же/похожим PN — предупредить до дозаполнения и до отправки, предложить открыть сравнение и зафиксировать решение продолжить.
10. Если карточка недоступна для редактирования в текущем реальном статусе НК, объяснить, какое действие необходимо (например, открыть новую черновую версию опубликованной карточки там, где это допустимо), не выдавать локальную запись за опубликованное обновление.

## 10. Поиск точных и похожих PN

### 10.1. Обязательные точки проверки

- Перед созданием нового GTIN.
- Перед созданием новой карточки с уже указанным GTIN.
- При импорте Excel, в том числе дубли **внутри текущей партии**.
- При массовой доработке существующих черновиков, особенно при совпадении с опубликованными карточками.
- Перед массовой отправкой готовых новых карточек/черновиков.

### 10.2. Логика

- Сначала точное сопоставление по GTIN (если указан), затем по точному PN, затем по нормализованному PN, затем поиск похожих строк.
- Нормализованный индекс учитывает регистр, пробелы, различия дефиса/пробела, распространённые варианты записи и опечатки, но **не должен автоматически считать отсутствие дефиса доказательством идентичности товаров**.
- Для радиоэлектроники отдельная буква или цифра может менять изделие, поэтому эвристика выдаёт **кандидатов и объяснение сходства**, а не юридическое/товарное заключение.
- Ограничить шум: показывать несколько самых значимых совпадений, сильные/слабые сигналы и возможность открыть полный список.
- Указываются PN, GTIN, название, статус, ТН ВЭД, ссылка на карточку/черновик и отличающиеся основные характеристики, если они есть.
- **Даже при точном совпадении PN** сотрудник может выбрать «Это другой товар» и продолжить после подтверждения; запись с сотрудником/датой/причиной сохраняется. При повторном действии по той же проверенной неизменённой версии не показывать одно и то же предупреждение бесконечно.
- Несовпадение PN при **полном совпадении GTIN** показывать как отдельный серьёзный конфликт идентификатора и требовать явной проверки, даже если правила продукта позволяют разные экземпляры/описания.
- На больших партиях — общий экран проверки, а не модальные окна по каждой строке.

### 10.3. Критерии против ложных решений

Автоматическое сходство не блокирует операцию навсегда и не является основанием создать новый GTIN. Все подтверждения аудируются. Порог сходства настраивается администратором в разумных границах, но прежде всего тестируется на реальных парах PN компании (точные, различие одной буквы, дефис, пробелы, совершенно разные модели).

## 11. GTIN: существующие и новые

- Если указан существующий GTIN: проверить структуру/контрольную цифру там, где применимо; сопоставить с карточками организации и известными внешними записями НК, проверить право использования/схему товара. Не изменять чужую опубликованную карточку без прав.
- Если GTIN отсутствует: сначала выполнить поиск дублей, затем определить **имеет ли организация право** выдавать новый код в НК, где находится мастер-система GTIN (НК или GS1), есть ли доступный диапазон и официальный поддерживаемый метод API.
- Отдельно различать российские GTIN и **импортные глобальные GTIN**. Не заставлять получать новый код, если законно используется существующий глобальный код импортного товара.
- Получение нового GTIN — отдельная операция с однозначным журналом, внешним результатом и защитой от дублей. При неизвестном исходе нельзя делать повторный запрос на новый GTIN до сверки.
- UI должен заранее показывать, какие новые GTIN будут запрошены, и требовать подтверждения партии; запрещено скрыто создавать коды в момент импорта XLSX.
- Если выдача через API/мастер-систему недоступна, показывать честный статус «Требуется получение GTIN через НК/GS1» и ссылку/экспорт необходимых данных. Это **ограничение интеграции**, не выполненная автоматизация; агент не может объявить полный цикл для таких карточек завершённым.

## 12. Жизненный цикл, отмена, архив, повторные действия

Хранить **два отдельных состояния**: (1) внешний статус карточки/версии в НК, (2) внутренний статус локальной работы/очереди. Не подменять внешний «Опубликована» локальным фактом успешной отправки подписи.

### 12.1. Основные переходы

| Внутренняя стадия | Следующее действие | Условие |
|---|---|---|
| Новая локальная | Проверить дубли → заполнить | Нет внешней записи либо ссылка на существующий черновик |
| Черновик/заполнение | Применить шаблон, редактировать, проверить | Поля и права доступны |
| Требует внимания | Исправить ошибки, разрешить предупреждения | Без автоматической отправки неподтверждённых строк |
| Готова к отправке | Создать/обновить версию в НК | Явное подтверждение сотрудника |
| Сохранение в НК | Ожидать результат/сверить внешний ID | Долговечная очередь, запрет слепых повторов |
| На модерации | Проверять статус | Только read-only запросы до внешнего результата |
| Требует изменений | Открыть замечания, исправить → снова на модерацию | Сохранить историю прошлой попытки |
| Ожидает подписания | Поставить операцию подписи/публикации | Подтверждённый статус НК и доступная УКЭП |
| Публикация выполняется | Проверить подтверждение от НК | Отправка не равна публикации |
| Опубликована | Просмотр; новая редактируемая версия там, где допустимо | Текущая опубликованная версия неизменна |
| Проблема синхронизации | Безопасная повторная проверка / разбор админа | Никакой слепой мутации |

### 12.2. Отмена ненужной операции

Предусмотреть понятную команду **«Остановить работу с карточкой/партией»** с указанием причины:

- Если действия ещё только локальные: остановить ожидающие задания, освободить локальные блокировки, поместить запись в локальный архив, **не удалять данные**.
- Если операция уже отправлена в НК: нельзя обещать её отмену. Заблокировать **новые** операции, отследить исход текущей, сообщить сотруднику, что она могла быть уже принята НК.
- Если карточка уже опубликована: локальная остановка/скрытие не равна архивированию/удалению карточки в НК. Изменение опубликованного статуса возможно только через реально разрешённую официальную операцию и отдельное явное подтверждение.
- При отмене одной строки массовой партии остальные независимые строки продолжают работу. Не отправлять её во второй раз, не создавать новый GTIN и не терять связь с общим batch.

### 12.3. Возврат из локального архива

- Администратор может восстановить локальную работу; сотрудник — свою локально остановленную запись, если внешнее состояние это позволяет.
- Возврат **не** возобновляет старую очередь автоматически. Сначала синхронизация с НК, проверка внешнего ID/версии, разрешённых действий и конфликтов; затем явное «Продолжить».
- При возвращении на редактирование использовать новую актуальную ревизию, а не устаревший снимок.
- Опубликованные карточки не должны пропадать из общего поиска из-за локальной архивной метки; архив — фильтр процесса, а не удаление нормативной записи.

### 12.4. Опубликованные карточки и новые версии

- Если карточка опубликована, а сотрудник хочет изменить разрешённые атрибуты, открывать отдельную черновую версию, сохранять опубликованную как действующую до подтверждённой повторной публикации.
- Поля, которые НК блокирует после первичного создания или публикации, в нашем UI read-only с понятным объяснением. Исправление обязательных неизменяемых атрибутов — через предусмотренную НК официальную процедуру/поддержку, а не самовольный `PATCH`.
- При новой модерации/публикации сохранять историю версий и дифф.

## 13. Матрица происхождения и изменения полей

| Поле / группа | Источник правды | Допустимые изменения | Ключевая проверка |

## 14. UI/UX: самостоятельный обязательный результат проекта

### 14.1. Не повторять ошибки первого `marking-bm`

Приложение проектируется **от рабочего сценария, а не от списка API-методов**. Длинная страница с последовательными техническими формами недопустима. Основная работа — короткий путь «найти карточку → увидеть проблему → исправить → проверить → отправить»; служебные сведения должны открываться по необходимости.

- Основной приоритет — настольный браузер Windows 10 Pro, рабочие разрешения 1366×768, 1440×900, 1920×1080, масштаб браузера 100–125%; на небольшом экране интерфейс должен быть доступен хотя бы для просмотра/легкого редактирования, без сломанных кнопок.
- Язык интерфейса русский. Идентификаторы PN/GTIN/TН ВЭД выводить точно; длинные значения могут быть усечены визуально, но всегда копируемы целиком.
- Максимум одна ведущая кнопка действия на текущей стадии. Массовые действия в панели выбора, не в каждой строке одновременно.
- Основные метрики и действия видны **в первом экране**, без необходимости прокручивать огромные блоки.
- В реестре закрепить заголовок и колонку PN; фильтры и поиск доступны постоянно. Горизонтальная прокрутка внутри таблицы допустима при действительно множестве колонок, но не должна скрывать идентификатор товара и действия.
- Разделять состояния: нет карточек, загрузка, нет результатов фильтра, ошибка API, офлайн, конфликт версии, недостаточно прав, операция выполняется, частично выполнено, нужна подпись.
- Не заменять объяснимые ошибки сырой JSON-структурой. Технический подробный код/идентификатор — в раскрываемом блоке «Детали».
- Не превращать все атрибуты в постоянно раскрытую простыню; группировать по смыслу и показывать недостающие.
- Цвет не является единственным способом сообщить статус: необходим текст, иконка/подпись. Контраст, focus state, клавиатура, заметные ошибки и сохранение несохранённых изменений обязательны.
- Один способ навигации и одна визуальная система для сотрудника и администратора; настройки администратора не отображаются обычному сотруднику вообще.

### 14.2. Информационная архитектура

**Главное меню сотрудника (рекомендованный порядок):**

1. **Карточки** — главный реестр и работа с одиночными карточками.
2. **Черновики** — сохранённый фильтр и массовое дозаполнение.
3. **Импорт Excel** — короткий мастер и результаты партий.
4. **Партии** — мониторинг массовых операций (создание, модерация, публикация).
5. **Шаблоны** — просмотр утверждённых шаблонов по ТН ВЭД; предложения новых версий для администратора.

**Только администратор:** «Администрирование» с подразделами: подключение НК, экспорт каталога, импорт/утверждение шаблонов, пользователи, очереди/подпись, аудит, архив локальных задач, резервное копирование, сведения о версии приложения/развёртывании.

Допускается уточнение названий при UX-прототипировании, но нельзя смешивать операции сотрудников и технические настройки на одном длинном экране.

### 14.3. Главный экран — компактный реестр

Требуемая компоновка desktop:

```text
┌────────────────────────────────────────────────────────────────────────────────────┐
│ Менеджер НК                   Последняя синхр.: 14:35      Поиск [ PN / GTIN ... ] │
├─────────────┬──────────────────────────────────────────────────────────────────────┤
│ Карточки    │ Карточки  [Все] [Черновики] [Требует внимания] [На модерации]       │
│ Черновики   │ [ТН ВЭД ▼] [Статус ▼] [Ответственный ▼] [Шаблон ▼]  [+ Создать]    │
│ Импорт      │  □  PN          GTIN           ТН ВЭД      Статус       След. шаг    │
│ Партии      │  □  L-132XYD    0464…         8536…       Черновик     Дополнить   │
│ Шаблоны     │  □  PSU-240     отсутствует    8504…       Дубль?       Проверить   │
│             │  □  CON-084     0464…         8536…       Модерация    Ожидание   │
│             │      ...                                                               │
│             │ [Выбрано: 12] [Применить шаблоны] [Проверить] [Отправить ▼]         │
└─────────────┴──────────────────────────────────────────────────────────────────────┘
```

**Необходимо показать:** PN, наименование (с разумным усечением), GTIN, полный ТН ВЭД (с раскрытием), внешний статус, внутренний статус/проблему, готовность обязательных полей, текущую следующую операцию, ответственного, время обновления. Не пытаться расположить 20 колонок в видимой области; второстепенные доступны через настройку колонок/детали.

Поведение:

- Поиск PN/GTIN/наименования с быстрыми результатами; строковые идентификаторы не теряют нули.
- Фильтры по внешнему и внутреннему статусу, ТН ВЭД, категории, типу, ответственному, партии импорта, наличию шаблона, наличию дубликатов и незаполненных полей.
- Сортировка, пагинация либо виртуализация для тысяч карточек, сохранение фильтров/ширины колонок в профиле.
- Чекбоксы массового выбора сохраняют явно выбранный набор между страницами и показывают его точное количество. Действие над «всеми результатами поиска» требует отдельного подтверждения, не трактуется как выбор видимых 20 строк.
- Клик по строке открывает боковую панель **без потери поиска, фильтров и позиции прокрутки**.
- Панель массовых действий показывает только допустимые действия для всей выборки; если часть карточек не подходит, перед отправкой — сводка по применимости.

### 14.4. Правая панель редактирования

Для desktop приблизительно 35–45% ширины, с возможностью расширения на весь экран. Слева реестр остаётся читаемым. Содержимое панели:

```text
┌──────────────────────────────────────────────┐
│ ←  PSU-240                         [Развернуть]│
│ Черновик НК | GTIN нет | ТН ВЭД 8504408300  │
│ Не заполнено 3 обязательных поля            │
│ [Основное] [Характеристики] [Проверки] [История] │
│                                              │
│ Наименование           [_________________]   │
│ Бренд                  [______________▼__]   │
│ Мощность               [____] [Вт ▼]         │
│ ⚠ Страна производства: обязательно          │
│                                              │
│ Предложения шаблона: 5 заполнено, 2 вручную│
│                                              │
│ [Сохранить]  [Проверить]  [Следующая →]      │
└──────────────────────────────────────────────┘
```

- Сверху: идентификация товара и текущая версия/статус; закреплённая панель действий снизу, чтобы кнопки не уходили из видимой зоны.
- Вкладка «Характеристики» — смысловые группы с индикатором количества обязательных незаполненных; справочники — searchable combobox, единицы измерения валидируются.
- Вкладка «Проверки» — список блокирующих ошибок и предупреждений с кликабельным переходом к конкретному полю; сравнение дублей side-by-side.
- Вкладка «История» — действия сотрудника и квитанции НК отдельно от редактируемых полей.
- Переход «Следующая» по текущей выборке/фильтру с сохранением/предупреждением о несохранённых изменениях.
- При конфликте ревизии — сравнение локальных и внешних изменений, кнопки «Обновить с НК» и «Сохранить локальную копию для разбора»; запрещён тихий overwrite.

### 14.5. Экран «Черновики» и массовое дозаполнение

Не отдельная гигантская форма, а преднастроенный реестр с видимым верхним блоком: **Всего / Можно дозаполнить / Требует человека / Отправлено на модерацию**. После выделения карточек — мастер «Применить шаблоны»:

1. Группы по ТН ВЭД, проверка наличия утверждённых шаблонов.
2. Предпросмотр изменений `было → предлагается`; отдельно пустые, конфликтующие, несопоставленные значения.
3. Подтверждение; синхронизация; итог по каждой карточке.
4. Кнопка «Отправить готовые» (с точным количеством и дополнительным подтверждением), неотправленные остаются доступными для ручной работы.

В группе ошибок можно нажать «Открыть следующую проблемную» и последовательно обработать список.

### 14.6. Экран поиска и подтверждения возможных дублей

- Не более одного агрегированного диалога на партию.
- Для каждого проблемного PN: **новая карточка слева, кандидаты справа** с GTIN, статусом, названием, ТН ВЭД и отличающимися характеристиками.
- Действия: «Открыть существующую», «Доработать существующий черновик», «Это другой товар, продолжить»; причина предупреждения и имя подтвердившего видны.
- После подтверждения возвращаться в исходный процесс без потери ввода и фильтров.

### 14.7. Мастер Excel и импорт шаблонов

- Пошаговый интерфейс с короткими этапами, прогрессом и кнопками «Назад/Далее».
- Не отображать все поля сопоставления разом, сначала показать распознанные, затем «Не сопоставлено / Исправить».
- Предпросмотр итогового набора перед внешней записью.
- Импорт шаблона агента — отдельный экран с результатами проверки/диффом и действием «Отправить администратору на утверждение»; у сотрудников не должна появляться возможность активировать произвольный JSON.

### 14.8. Экран партий и очереди

Видимая пользователю партия с прогрессом: «100 карточек: 60 опубликовано, 20 на модерации, 15 требуют исправлений, 5 ожидают подписи». Показывать результаты по строкам, причины ошибок, возможность безопасной проверки результата, экспорт списка ошибок. Никакого «успех» на основании одного HTTP 200 без подтверждённого изменения статуса карточки.

### 14.9. Админка

Отдельные вкладки:

- **НК и организация:** статус подключения, разрешённые товарные группы, схема, последняя синхронизация, обновление токена, безопасные read-only тесты.
- **Шаблоны:** реестр по ТН ВЭД, импорт JSON, preview/diff, утверждение, версионирование, откат.
- **Подпись:** heartbeat Windows-подписанта, отпечаток/срок сертификата, очередь, ошибки, ручной разбор неизвестного результата.
- **Операции:** зависшие задания, журнал внешних ID, корреляция попыток, безопасное возобновление.
- **Пользователи и права**, **Резервные копии**, **Диагностика и версия**.

На экранах сотрудника эти технические разделы отсутствуют, включая ссылку на админку.

### 14.10. UX-состояния и показатели качества

Проверить в браузере (не только unit-тестами): пустой каталог, 1 карточка, 100+ записей, медленный API, потеря сети, 422/400 с полями, 401, 403, 429, 500, неуспешная модерация, 20 найденных дублей, отсутствие шаблона, противоречие локальной и серверной версий, выключенный подписант, выполнение разных задач в соседних вкладках, масштаб 125%, светлая/тёмная тема при наличии общей темы. Не допускать потери введённого текста при закрытии панели или ошибке соединения.

Проверяемые UX-критерии: главные задачи доступны максимум в 1–2 навигационных шага от реестра; пользователь видит **следующее действие** и **почему оно недоступно**; ошибки ведут к конкретной строке/полю; в обычном сценарии для заполнения последовательных карточек не требуется каждый раз возвращаться к верхней части таблицы; ни одно действие изменения данных НК не совершается при простом открытии карточки.

## 15. Архитектура и переиспользование готовых проектов

### 15.1. Реальные репозитории-источники

- [`AlexSapronov/marking-bm`](https://github.com/AlexSapronov/marking-bm) — приоритетный ориентир инфраструктуры: FastAPI, server-side auth, роли, SQLite WAL, durable outbox/worker, ошибки, серверная подпись через Windows-подписант, админка, резервные копии и проверки обновления. **Не копировать весь UX без переосмысления**.
- [`AlexSapronov/gis-trueapi`](https://github.com/AlexSapronov/gis-trueapi) — отдельные готовые решения доступа к ГИС МТ/True API, справочники и проверки кодов, если применимы к конкретной интеграции НК.
- [`AlexSapronov/km-split`](https://github.com/AlexSapronov/km-split) — справочный код криптографической подписи, формирование неизменяемых signed payload и сохранение квитанций; **не переносить** специфику разделения КМ и эмиссии.

Сначала изучить исходники и текущие версии репозиториев; в отчёте явно указать, **какие модули/паттерны переиспользованы**, а какие написаны заново. НК — отдельная система API, токены True API/СУЗ не считаются автоматически допустимыми для НК.

### 15.2. Рекомендуемая техническая схема

```text
Сотрудники Windows/браузер (корпоративная сеть)
              │ HTTPS
              ▼
        Ubuntu VPS · nk-manager
        ├─ FastAPI + русскоязычный Web UI
        ├─ API адаптер Национального каталога
        ├─ Сервис карточек / шаблонов / похожих PN
        ├─ Импорт XLSX, экспорт JSON/XLSX/ZIP
        ├─ БД + версии + audit + durable outbox
        └─ Очередь внешних операций / status polling
              │                         ▲
              │ HTTPS к НК              │ подпись / auth
              ▼                         │
       Национальный каталог       Windows-подписант
                                  CryptoPro + Рутокен
```

Возможный стек — Python 3.12/FastAPI, HTML/CSS/JavaScript, SQLite WAL с аккуратными транзакциями при умеренных нагрузках. Если агент обоснованно выберет другой стек или PostgreSQL, согласовать последствия для VPS 60 ГБ, развёртывания и поддержки; изменение стека не должно быть самоцелью.

Новый проект должен иметь отдельные конфигурацию, каталог установки, БД, службу `systemd` и базу тестов. Не выбирать порт, не проверив занятые сервисами `marking-bm`, `gis-trueapi` и `km-split`. Использовать корпоративный HTTPS с reverse proxy; прямой внешний доступ к серверу не нужен.

### 15.3. Централизованная подпись

На рабочем Windows-ПК администратора уже действуют КриптоПро, Рутокен, подпись в браузере и сторонних программах; нет прав локального администратора. Подписант должен использовать уже доступные компоненты, по возможности без системной установки. VPS имеет root-доступ через SSH.

- Изучить действующий `marking-bm/signer/Start-Signer.ps1` и протокол, проверить совместимость с **точным форматом подписи НК**. Не считать, что схема СУЗ один в один подходит НК.
- Предпочтение — общий защищённый сервис подписи или независимо работающий адаптер того же принципа. Не создавать неподконтрольный второй процесс, соревнующийся за один аппаратный ключ. Выбрать и документировать способ координации.
- Подписание запускается автоматически насколько допускают Рутокен, КриптоПро, PIN/политики Windows; ключ и PIN остаются на ПК/токене, никогда не передаются VPS.
- Сервер подписывает **строго подготовленные разрешённые типы операций**, с hash, типом, ID, автором, ревизией, контекстом; произвольный подписываемый текст от сотрудника запрещён.
- Выключенный ПК/отсутствующий токен → статус «Ожидает подписи» без потери операции. Наличие подписанта не заменяет право сотрудника инициировать публикацию.
- Фактическая работа на конкретном ПК и подписание реального запроса проверяются отдельно; автотесты не являются доказательством аппаратной подписи.

### 15.4. Надёжность внешних действий

- Долговечная очередь/outbox, переходы `prepared → signing → signed → dispatching → submitted → confirmed`, плюс `unknown`, `blocked`, `failed`; названия допустимо адаптировать.
- Каждая команда имеет локальный уникальный ключ, неизменяемый payload/hash, контекст карточки и ID ревизии. Двойное нажатие, обновление страницы или восстановление после рестарта не создают вторую карточку или второй GTIN.
- **Перед отправкой мутации** сохранить состояние намерения; при потере ответа после отправки не повторять мутацию, пока не выполнена безопасная сверка внешнего состояния.
- Статусы проверяются по read-only методам, с лимитами/экспоненциальной задержкой и отдельной квотой для новых задач, чтобы старые ожидающие не блокировали новые.
- При массовой операции частичные успехи сохраняются поштучно. Ошибка одной карточки не отменяет успешные операции соседних карточек и не вызывает повторную отправку уже созданных.
- Если внешняя схема НК не предоставляет идемпотентность/достаточно данных для восстановления, соответствующую ситуацию пометить `unknown` и вынести в разбор администратора. Не скрывать её зелёным статусом.
- Сохранять квитанции, сообщения модератора, API errors и request ID, но маскировать токены и конфиденциальные данные.

## 16. Безопасность, данные, backup и мониторинг

- Одна корпоративная организация. Администратор управляет разрешениями, адресами контуров и сертификатом; секреты только в защищённых конфигурациях/файлах, не в Git и не в JS браузера.
- HTTPS, CSRF, secure/httpOnly cookies, защита от перебора админского пароля, ограничение размера файлов, проверка MIME/содержимого и безопасные имена; валидировать XLSX/JSON на сервере.
- Авторизация на каждую операцию и просмотр файлов; отдельный токен подписанта. Административная сессия требует отдельный пароль, не зависит от введённого username.
- Журнал: кто, что, в какой версии, когда, почему, каким файлом/шаблоном изменил; журнал внешних действий и подтверждений возможных дублей.
- Регулярные online backup базы + файловых артефактов; обязательная **проверка восстановления** в отдельный путь/на отдельном экземпляре, который не может отправлять реальные API-команды.
- VPS 60 ГБ, разделяемый с другими проектами. Мониторинг свободного диска, размера БД/вложений, очереди, состояния токенов, доступности подписанта, давности последней синхронизации. **Не удалять карточки/файлы автоматически** ради экономии места.
- Отдельно контролировать лицензии, хранение коммерческой информации в экспортируемых данных, полномочия УКЭП; ключ принадлежит администратору и может подписывать действия сотрудников только в согласованных организацией рамках.

## 17. Установка и обновление: обязательная воспроизводимость

Предусмотреть Ubuntu VPS внутри корпоративной сети и Windows 10 Pro без прав администратора для подписанта. В поставке должны быть:

1. `.env.example` без секретов, `requirements-lock.txt` (или эквивалент закрепления зависимостей), `systemd` unit, конфигурация reverse proxy, отдельный непривилегированный системный пользователь и каталог данных.
2. `README` с командами первого развёртывания, проверки подключения, настройки подписи, резервного копирования, восстановления и **отката**.
3. Приложение/админка показывают `version`, полный `git commit SHA`, время сборки/запуска, путь установки/наименование сервиса (где безопасно), номер версии схемы БД и версию frontend-assets.
4. После `git pull`/обновления можно проверить, что **перезапущен именно нужный service**, Python-процесс использует нужный каталог, отдаются обновлённые JS/CSS, а браузер не удерживает старые статические файлы. Статические ресурсы должны быть версионированы или иметь корректный cache-busting.
5. Миграции БД идемпотентны, имеют план отката/восстановления. Перед обновлением создаётся backup; после него выполняется автоматический healthcheck и smoke test.
6. Диагностика ошибок без раскрытия токенов, PIN и приватного ключа. Документированные команды `status`, `logs`, `health`, `version`, проверка целостности очереди и зависших задач.
7. Независимость от существующих сервисов: установка нового проекта не ломает `marking-bm` и другие работающие приложения на VPS.

## 19. Набор обязательных приёмочных сценариев

Агент должен подготовить исполняемые unit/integration/browser тесты и отдельный чек-лист реального тестирования. Минимум:

### Каталог и синхронизация

1. Загрузить опубликованные карточки/черновики из НК, сохранить внешний ID и версии. Повторная синхронизация не создаёт дублей.
2. Одна карточка одновременно имеет опубликованную и черновую версии; в UI это один товар с двумя состояниями, редактируется только допустимая версия.
3. Изменение статуса через ЛК НК корректно появляется после синхронизации; локальные правки без предупреждения не затираются.
4. Ошибка/таймаут на странице N во время выгрузки: прогресс и уже полученные карточки сохранены, после восстановления загрузка продолжается.

### Шаблоны

5. Экспорт содержит реальные исходные атрибуты, их типы и полный десятизначный ТН ВЭД; JSON/XLSX и манифест согласованы.
6. Импорт корректного шаблона → preview → утверждение админом → использование в подходящей карточке.
7. Неизвестный атрибут, значение вне справочника, чужой ТН ВЭД/категория → ошибка до активации шаблона.
8. Обновление шаблона и откат: старые версии и ссылки на ранее применённую версию не исчезают.
9. Шаблон не переписывает уже заполненные атрибуты черновика и не копирует уникальные значения с других товаров.

### Новые карточки и Excel

10. Ручное создание карточки по ТН ВЭД и шаблону, поля проверяются до записи в НК.
11. Excel с произвольными заголовками, несколькими листами, текстовыми GTIN с нулями, пустыми значениями и несколькими ошибками корректно сопоставляется и разбирается.
12. Загрузка файла 100 товаров → корректные строки создаются, ошибки видны по строкам, повторная попытка не дублирует успешные карточки.
13. Нет GTIN → сначала поиск дублей; новый GTIN создаётся только после отдельного подтверждения и при наличии прав/метода.
14. Неизвестный исход запроса нового GTIN → повторное получение блокируется до сверки.

### Дубли

15. Тот же PN: точное совпадение с опубликованной карточкой → предупреждение, просмотр сравнения, разрешённое подтверждение продолжения с аудитом.
16. Близкие PN `L-132XYD` и `L132-XYD` → кандидат; `L-132XYD` и `L-132XYE` → предупреждение без автоматического признания одним товаром.
17. Черновик дублирует опубликованную карточку: массовое заполнение предлагает сверку, не создаёт новый GTIN молча.
18. 20 предупреждений в Excel не вызывают 20 последовательно блокирующих окон; есть общий список для разбора.

### Черновики, модерация, публикация

19. Выбрать 50 существующих черновиков, применить шаблоны: используются **их же внешние ID/версии**, а заполненные значения не затронуты.
20. В группе часть карточек остаётся неполной: подготовленные можно отправить, остальные остаются «Требует внимания» с конкретными полями.
21. Отказ модерации с замечанием к атрибуту → показывается комментарий возле поля; исправление и повторная модерация не создают новую карточку.
22. Доступна подпись, Windows-подписант включён → отправка и **подтверждение опубликованного статуса НК**. Если подписант выключен — безопасное «Ожидает подписи».
23. Опубликованная карточка: доступные изменения оформляются новой версией; старый опубликованный вариант не меняется до повторной публикации.

### Роли, отмены, сбои

24. Сотрудник может массово публиковать без одобрения администратора; изменить конфигурацию НК/сертификата/утвердить шаблон не может даже через прямой URL/API.
25. Два сотрудника редактируют одну ревизию: второй не затирает изменения первого.
26. Остановлена одна строка партии из 100: остальная партия продолжается; уже отправленная в НК операция не объявляется «отменённой» без доказательства.
27. Возврат из локального архива не перезапускает старые мутации, сначала сверяет НК.
28. Таймаут после внешней отправки → `unknown`, без слепого повторного создания карточки, GTIN или публикации.
29. Множество зависших проверок не задерживает новые задания; очередь переживает перезагрузку сервиса.
30. Бэкап восстановлен на отдельной БД; восстановленный сервис **не** совершает реальные внешние операции.

### UI/UX и развёртывание

31. Полная работа в реестре на 1366×768 без длинного вертикального полотна и исчезнувших главных действий.
32. Боковая панель открывается из строки и закрывается без потери фильтра, выделения и позиции списка; переход «Следующая» доступен.
33. Ошибка указывает поле и позволяет перейти к нему; нет технического JSON вместо объяснения.
34. Выбор 100 карточек на нескольких страницах соответствует фактическому набору, подтверждение массовой операции показывает точное число.
35. После деплоя видно фактический commit, версию backend/frontend, системный сервис и результат smoke; браузер действительно получает актуальные JS/CSS.
36. Подписант проверен на реальном Windows-ПК с уже установленными КриптоПро и Рутокеном; ограничения политик/PIN документированы. Без фактической проверки не отмечать пункт «подпись работает».

**Критерий успешной промышленной приёмки:** один согласованный реальный товар проходит полный маршрут от локального черновика/создания до статуса «Опубликована» в НК; отдельно одна существующая реальная черновая карточка дорабатывается без смены ID; затем безопасная небольшая массовая партия проходит те же проверки. Если конкретный API шаг объективно недоступен, результат формально «частично реализовано, есть ограничение», а не «всё готово».
