# Рабочий локальный запуск в WSL2

Версия 0.2.0: настоящее приложение FastAPI/SQLite, без деморежима и вымышленных карточек. Вход, сохранение, импорт XLSX, шаблоны и экспорт работают на локальных данных. **Прямое API НК, выдача GTIN, модерация, подпись и публикация ещё не подключены.** Это не завершённая промышленная интеграция НК.

## Первый запуск

Откройте Ubuntu/WSL2. Рекомендуется Python 3.12. Исходники и базу храните в домашнем каталоге Linux, не в `/mnt/c`.

Если репозитория ещё нет:

```bash
cd ~
git clone --branch codex/wsl-workspace https://github.com/AlexSapronov/nk-manager.git
cd ~/nk-manager
```

Если `~/nk-manager` уже существует, проверьте незакоммиченные изменения через `git status`, затем переключитесь на поставляемую ветку:

```bash
cd ~/nk-manager
git fetch origin
git switch codex/wsl-workspace
git pull --ff-only
```

До слияния PR используйте именно эту ветку. После слияния те же файлы доступны в `main`; не смешивайте команды от статического прототипа и рабочего приложения.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements-lock.txt
.venv/bin/python scripts/setup.py
.venv/bin/python scripts/run_wsl.py
```

`setup.py` спросит username (по умолчанию `alexander`) и новый отдельный пароль администратора длиной от 12 символов. Пароль вводится скрыто и не передаётся аргументом команды. Повторный запуск настройки не меняет существующие данные или пароль.

Откройте **http://localhost:8020** в браузере Windows.

- Сотрудник: указанный username, поле пароля пустое.
- Администратор: тот же username и заданный отдельный пароль.
- Админка появляется только после административного входа; сервер проверяет права независимо от интерфейса.
- Закрытие терминала останавливает сервис; для остановки в открытом терминале — `Ctrl+C`.

Запуск выполняется без `--reload`, с одним worker и настоящей постоянной БД. Node.js, npm и КриптоПро для этого выпуска не нужны.

Если порт 8020 занят, launcher ничего не останавливает и предлагает другой:

```bash
.venv/bin/python scripts/run_wsl.py --port 8021
```

Тогда в Windows откройте `http://localhost:8021`. Не используйте занятые другими приложениями 8000/8010 автоматически. Сервис слушает только loopback WSL, не `0.0.0.0`.

Если `venv` сообщает об отсутствии `ensurepip`, в Ubuntu нужен установленный пакет `python3-venv`. Это зависимость Linux/WSL, не установка компонентов Windows. Если у пользователя WSL есть sudo: `sudo apt install python3-venv`. Если Windows не открывает localhost, сначала проверьте в WSL `curl http://127.0.0.1:8020/health`: это отделяет проблему сервиса от проброса WSL2.

## Что потыкать на реальных данных

1. Войти и создать локальную карточку: PN обязателен, неизвестный GTIN оставьте пустым. Он не генерируется.
2. Импортировать XLSX через четыре шага. Выбрать лист, строку заголовков и PN/GTIN/ТН ВЭД. Остальные колонки становятся характеристиками.
3. Если в отчёте нет категории/типа/ТН ВЭД, во втором шаге раскрыть «Общие значения» и указать только известные значения. Они заполняют лишь пустые поля и фиксируются в происхождении.
4. Строки с формулами, невалидным GTIN или ТН ВЭД не принимаются. Предупреждение PN можно разрешить с причиной. Выбор строк и подтверждение явные.
5. Открыть импортированную карточку → «Взять в работу» → изменить локальные поля → «Сохранить». Перезагрузить страницу и убедиться, что значения остались.
6. Проверить поиск, фильтры, выбор между страницами, локальный архив, историю и темы.
7. В разделе «Шаблоны» скачать корпус для анализа. Затем импортировать предложенный JSON, административным входом утвердить локальную версию и из реестра просмотреть план дозаполнения.

Все правки отмечаются локальными. Снимок опубликованного статуса из XLSX не становится свежим статусом НК и не меняется при сохранении. Исходный снимок и история остаются доступны в карточке. Повторный импорт не затирает локальные правки; строки с конфликтом требуют разбора.

Уже успешно принятый файл повторно не импортируется по SHA-256. Если партия принята частично, исправьте источник/создайте отдельный исправленный файл для оставшихся строк и снова просмотрите совпадения. Не повторяйте исходный файл в надежде создать те же записи заново.

## Как выгрузить таблицу для создания шаблонов категорий

Для анализа нужны полные характеристики реальных опубликованных товаров:

1. В личном кабинете НК откройте «Товары» и в фильтре выберите одну конкретную категорию.
2. «Экспорт» → «Скачать полный отчёт (.XLSX)».
3. Повторите для других категорий. Сохраняйте исходные заголовки, GTIN и значения без ручного преобразования Excel.
4. Можно **сразу передать эти XLSX в чат**. Импорт в наше приложение для первичного анализа не обязателен.
5. Либо импортируйте их в менеджер и нажмите «Шаблоны» → **«Выгрузить весь каталог для анализа»**. Пришлите `nk-catalog-analysis.zip`.

ZIP содержит:

- `catalog.json` — все локальные поля, характеристики и исходные снимки;
- `summary.xlsx` — строковую таблицу с характеристиками (до 230 колонок характеристик; полный набор остаётся в JSON);
- `manifest.json` — количество, распределение по ТН ВЭД, контрольные суммы и сведения об ограничениях XLSX;
- `schema.json` и `README.txt` — описание корпуса и задания внешнему агенту.

Токены, пароли и сессии в экспорт не входят. Коммерческие сведения из самих карточек входят — состав выгрузки можно проверить перед передачей. Не присылайте файл базы SQLite вместо выгрузки: в нём хранятся доступы к локальному приложению.

Официальная [инструкция экспорта НК](https://markirovka.ru/knowledge/tovarnye-gruppy/obschie-voprosy-gis/kak-massovo-vygruzit-kartochki-s-natsionalnogo-kataloga), обновление 28.07.2026: полный отчёт доступен по выбранной категории и опубликованным карточкам; технические карточки в отчёты не входят. Для более 5000 опубликованных карточек инструкция направляет в поддержку НК. Краткий отчёт не заменяет полный корпус характеристик.

## Данные, повторный запуск, обновление

По умолчанию база находится в `~/nk-manager/data/nk-manager.sqlite3`. Исходные XLSX, планы, строки, аудит и шаблоны — в этой же БД. Данные не отправляются на облачный сервис автоматически. Не удаляйте `data`, не создавайте вторую независимую рабочую копию базы без понимания последствий.

Повторный запуск:

```bash
cd ~/nk-manager
.venv/bin/python scripts/run_wsl.py
```

Проверка версии: `http://localhost:8020/health`; полный commit, assets и схема БД также видны в админке. HTML и JS/CSS получают `no-store`, assets имеют hash в URL.

Перед обновлением сделайте снимок в новый файл (путь должен ещё не существовать):

```bash
cd ~/nk-manager
.venv/bin/python scripts/backup.py data/nk-manager.sqlite3 backups/before-update-20261024.sqlite3
```

Затем остановите сервис, выполните `git pull --ff-only`, установите закреплённые зависимости и снова запустите launcher. `setup.py` повторно не нужен. Текущая схема БД — версия 1; будущие несовместимые изменения потребуют отдельной миграции.

Восстановление — только при остановленном сервисе, в новый каталог:

```bash
.venv/bin/python scripts/backup.py backups/before-update-20261024.sqlite3 restored/nk-manager.sqlite3
.venv/bin/python scripts/run_wsl.py --data "$PWD/restored"
```

Скрипт проверяет SQLite integrity/foreign keys и удаляет старые сессии из снимка. Потребуется повторный вход; сам пароль администратора сохраняется как hash. В этом выпуске внешних API-мутаций нет, поэтому восстановленная копия не может отправить старую очередь.

Не используйте команды `git reset --hard` для обновления с несохранёнными изменениями. Откат к совместимому commit выполняйте при остановленном сервисе; исходную БД сохраняйте отдельно, восстановление всегда в новый путь.

## Что ещё не реализовано

Прямой read-only API НК, актуальные схемы/ID атрибутов, получение GTIN, настоящая модерация, УКЭП/Windows-подписант, подтверждённая публикация и промышленная очередь. Кнопки интерфейса не имитируют эти операции. Работа именно на вашем Windows/WSL2 ещё должна быть проверена локальным запуском; тесты выполнялись в Linux.
