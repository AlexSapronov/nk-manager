# Код-ревью nk-manager: 30.10.2026

## Охват

Проверены FastAPI (main.py), SQLite/store, NK API/очередь,
импорт/нормализация/шаблоны, создание массовых партий, подписант,
web интерфейс, CSS, маршруты WSL/VPS и текущие Python/Playwright CI.
Система ориентирована на **десктоп**, не на мобильную работу.

Это статическое ревью исходного кода с синтетическими интеграционными
тестами, **не** нагрузочный тест промышленного НК и не доказательство
времени отклика в конкретной рабочей базе.

## Исправлено в PR #22

| Синхронизация | Каждый запрос начинал обход с 2000 года | Быстрый режим с 2-дневным перекрытием, минимальная пауза между повторными ручными запросами, отдельная полная сверка |
| Синхронизация | Одно обращение списка на 25 карточек и запись даже неизменившихся снимков | Страница списка 100, детали пакетами по 25; пропуск неизменившихся JSON |

## Оставшиеся проблемы и приоритеты

### P0. Проверка в промышленном контуре

- Проверить временные фильтры `from_date/to_date` для действительно
  **изменённых** товаров в НК. Пока требуется полная сверка после
  длительного простоя/смены статуса или при сомнениях в полноте API.
- Проиграть полную перестройку **на копии боевой базы** с реальным ключом:
  количество карточек, случаи пропуска/404/429, восстановление
  файлов из закрытой резервной копии. Запрещено проводить эту проверку
  непосредственно на единственной рабочей базе.
- Перед сбросом сервис обязан остановить новые внешние отправки,
  проверить отсутствие незавершённых операций и сохранить
  неизменяемые квитанции/аудит.

### P1. Избыточный размер первоначального реестра

`/api/cards` до сих пор возвращает полные JSON attributes +
source_snapshot для **каждой** карточки. Уже при нескольких тысячах
товаров это большой объём сериализации и сетевой передачи даже с
инвалидацией. Следующее изменение: отдельный API краткого индекса
карточек с пагинацией и серверным поиском по PN/GTIN/статусу;
подгружать полную карточку по ID только при открытии редактора.

Важно: поиск PN обязан оставаться **точным**, с учётом всех символов;
подстроковый поиск использовать только как фильтр интерфейса,
а не как проверку совпадения артикулов.

### P1. Серверные операции большого объёма

- `draft_workflow.workspace` многократно строит справочник видов и
  рассчитывает нормализацию всех черновиков. Кэшировать справочник
  по ревизии подтверждённых NK-снимков и вычислять готовность
  только нужной страницы/сегмента.
- `normalization_service.apply` заново выбирает полный список
  карточек при обработке каждой строки. Вынести базовый индекс
  за цикл и применять изменения к нему в пределах транзакции.
- `bulk_creation.existing` может сканировать все dirty NK-карточки
  для каждого PN. Нужен индекс актуальных подтверждённых ключей
  (GTIN + PN + бренд + ТН ВЭД) и пакетная сверка.

### P1. Управление рабочими состояниями

Показывать не технические `prepared/submitted/unknown`, а
понятные этапы: «проверяем», «готово», «требуется действие», с
кнопкой просмотра подробностей ошибки. Не скрывать ошибку
внутри технических вкладок. Добавить постоянную панель
прогресса крупных партий и независимое обновление таблицы
без сброса фильтров, сортировки и открытого редактора.

### P2. Архитектура интерфейса

- `web/live.js` остаётся большим монолитным файлом. Разделить
  реестр, редактор, импорт, администрирование и модальные сценарии.
- HTML строится длинными template strings, что усложняет локальное
  тестирование состояний и доступность. Ввести UI-компоненты
  и согласованный набор шаблонов.
- Унифицировать состояния кнопок (loading, disabled, подтверждение),
  высоту полей, футеры диалогов, таблицы и приоритет основных действий.
- В режиме рабочего десктопа отдельно проверить 1366×768, 1440×900,
  1920×1080 и 125% масштаба браузера. Мобильную версию
  не считать обязательным критерием.

### P2. Эксплуатация

- Добавить замеры P50/P95 времени /api/cards, /api/drafts/workspace,
  размера JSON, времени списка и запросов к НК на 1000/5000/10000 карточек.
  Сейчас без этих метрик **невозможно** честно дать процент ускорения.
- Для восстановления обеспечить отдельную ручную
  документированную процедуру «вернуть SQLite из backup»
  с остановкой сервиса и целостностью WAL.
- После принятия PR #21 GS1 восстановление должно пользоваться
  теми же правилами блокировки при перестройке каталога и тем же
  механизмом истории операций. Нельзя запускать PR #21 и PR #22
  параллельно без разрешения конфликтов `nk.py/main.py/web/live.js`.

## Безопасность и сохранность

При полном сбросе удаляется только **активное локальное товарное
пространство** (карточки/снимки/импорты/собственные шаблоны и планы).
Пользователи, ключ НК, сертификат, история запросов/квитанций
и неизменяемый аудит намеренно сохраняются. Это не полное удаление
всех персональных сведений с сервера. Резервная копия содержит
старые бизнес-данные и хранится с правами 0600 внутри каталога
данных сервиса. Её жизненный цикл и срок хранения следует согласовать.
