# Архитектура — решения этапа 0/1

## Сейчас

Самостоятельный статический прототип HTML/CSS/JS. Вымышленные fixtures живут только внутри `prototype/app.js`, серверной логики нет. `preview.html` — производная автономная сборка тех же исходников. Данные сессии не персистируются, авторизации и внешних вызовов нет.

## После согласования UX

FastAPI / Python 3.12, обычный JavaScript, SQLite WAL при умеренной корпоративной нагрузке. Отдельные `/opt/nk-manager`, `/var/lib/nk-manager`, `nk-manager.service`, непривилегированный пользователь и секреты вне Git. Производственный порт заранее не закреплён: перед установкой проверить `ss -ltnp` и units существующих приложений. В README доноров и marking-bm, и km-split упомянут порт 8010 — копировать его без проверки нельзя.

Сущности: catalog_items, card_versions, typed attributes/provenance, versioned schemas, template_versions, import_batches/rows, exports, duplicate_candidates/decisions, immutable operations/receipts, audit, assignments и attachments. GTIN и ТН ВЭД — строки. Уникальность внешнего ID + версии; GTIN не использовать как единственный ключ корпоративного экземпляра карточки. Опубликованный и черновой варианты показываются одной логической записью.

Изменения: optimistic revision + транзакционное назначение ответственного; stale revision → conflict, без overwrite. Применение шаблона — сначала план, затем заполнение только пустых допустимых полей. Внешние значения и локальные предложения хранятся раздельно.

Очередь: неизменяемые payload/hash, user/context/revision и уникальный ключ команды. До запроса сохраняется dispatching. После потери ответа — unknown и read-only сверка; мутации не повторяются автоматически. У новых задач и polling отдельные квоты. Остановка запрещает новые задания, сохраняет уже полученный результат и не обещает отменить принятый запрос НК. Восстановление архива не перезапускает старую очередь.

Авторизация: username сотрудника из заранее созданных учётных записей; полномочия админа — отдельный пароль и серверная сессия. Все права на сервере, CSRF, secure/httpOnly cookies и rate limit входа. Публикация разрешена сотруднику, утверждение шаблонов — администратору.

## Решение по подписанту

Цель — один брокер на Windows, последовательно обслуживающий allowlist операций нескольких приложений, с межпроцессной блокировкой аппаратного ключа и отдельными полномочиями каждого приложения. До реализации нужно прочитать точную схему подписи НК и полный протокол действующего подписанта. Изменение существующего marking-bm и запуск второго конкурирующего процесса не авторизованы этой поставкой. Если совместимость не доказана, задачи остаются заблокированы; PIN и закрытый ключ на VPS не поступают. Аппаратная проверка на Windows обязательна отдельно.

## План эксплуатации

Корпоративный HTTPS/reverse proxy; online backup SQLite и вложений, SHA-256-манифест; restore в новый путь с внешними операциями disabled; миграции после backup, smoke после рестарта, откат к прежнему коду/совместимой БД. Commit SHA, версия схемы, backend/frontend/assets, service и build time в диагностике. Эти механизмы пока спроектированы, не реализованы.
